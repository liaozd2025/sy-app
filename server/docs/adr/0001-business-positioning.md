# ADR-0001：业务定位 = 纯 B 端培训平台

- **状态**：Accepted
- **日期**：2026-05-24
- **决策者**：产品负责人（grill 访谈 Q1）
- **相关**：[PRD §1](../../../docs/prd-v1.md#1-背景context)

## 背景 (Context)

项目初期存在定位模糊：现有原型 `apps/mobile` 充斥 C 端视感的健康内容（睡眠、节气、食材），但产品负责人口述目标用户是"一级经销商"。后端数据库表名也用了 `dh_live_member`（会员）这类中性命名，没有"dealer / distributor"等暗示。

三种候选定位：

- **A. 纯 B 端培训平台**：用户 = 一级经销商，健康内容只是知识弹药库
- **B. 纯 C 端品牌平台**：用户 = 终端消费者，经销商只是渠道入口
- **C. 双角色混合**：一个 App 两种身份

## 决策 (Decision)

**选 A：纯 B 端培训平台。**

- App 唯一用户群体：**一级经销商**
- 核心闭环：**看直播 → 学课程 → 答题 → 攒积分 → 兑福利**
- 健康内容定位：**经销商的知识弹药库**，帮助他们在终端用户面前更专业
- v1 **不做** C 端品牌内容、不做终端消费者账号、不做"分销裂变"

## 后果 (Consequences)

### 正面
- 整个产品形态收敛极快，所有功能围绕"学习赋能"即可
- 数据库设计无需引入"消费者 vs 经销商"双身份机制
- 现有"积分 + 必修 + 学习进度"DB 设计天然契合

### 负面
- 现有 mock 数据偏 C 端口吻，需要在 vibe coding 阶段逐步调整文案
- v1 没有终端用户触达，"经销商分发到客户"的杀手锏要推到 v2（见 ADR-0007）

### 影响范围
- `apps/mobile` 所有文案需偏 B 端培训语调
- `dh_live_member` 表保留命名（不重命名为 dealer），但需关联 organization
- admin-web 后台所有 UI 围绕"管理经销商学员 + 内容生产"
