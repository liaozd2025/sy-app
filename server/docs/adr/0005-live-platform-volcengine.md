# ADR-0005：直播形态 = 火山引擎裸用 + WebView 嵌入

- **状态**：Accepted
- **日期**：2026-05-24
- **决策者**：产品负责人（grill 访谈 Q5、Q9）
- **相关**：[ADR-0004](0004-live-course-decoupling.md), [PRD §5.4](../../../docs/prd-v1.md#54-直播模块仅嵌入式)

## 背景 (Context)

直播形态选型空间：

| 方案 | 描述 | 工期 |
|------|------|------|
| A. 完全自建 | 声网/腾讯 RTC 裸搭推流+UI | 8-12 周 |
| B. SaaS + WebView 嵌入 | 三方 SaaS 提供推流，我们 WebView 嵌 + 自建互动 | 4-6 周 |
| C. 云厂商 SDK | 腾讯云 LCIC 等，自建 UI 互动 | 6-10 周 |
| D. 录播伪直播 | 提前录好定时开放 | 1-2 周 |

现有原型 `live-screen` 标注"内嵌 H5" → 暗示已倾向 B 方案。
mock 数据有 `chat_message`, `material` → 一开始想自建互动模块。

但 grill 访谈第二轮产品负责人明确：**"直播的功能，包括聊天的这些功能，都是火山引擎自带的，我们不单独开发。"**

这进一步收敛了 B 方案的边界 —— 不仅不自建推流，**连聊天/资料/互动模块也不自建**。

## 决策 (Decision)

### 选型
- **三方 SaaS 供应商**：**火山引擎直播 (veLive 系列)**
- **接入方式**：v1 优先 **WebView 嵌入**火山提供的直播间 URL；原生 SDK 接入留 v2 评估

### 责任分割

| 功能 | 谁负责 |
|------|--------|
| 推流 / 转码 / CDN / 回放 | 火山引擎 |
| 直播间 UI（视频画面 + 聊天 + 互动 + 主播控制） | **火山引擎自带，我们不开发** |
| 直播场次预约 | **我们**（`dh_live_reservation`） |
| 学员观看记录 | **我们**（`dh_live_watch_record`，前端进入/退出上报） |
| 直播详情页（封面、简介、主讲人、状态、进入按钮） | **我们** |

### Schema 变更
- **删表** `dh_live_chat_message`（v1 不建，火山自带）
- **删表** `dh_live_material`（v1 不做资料下载，老师直播内发二维码）
- 后端定义 `LivePlatformAdapter` 抽象接口，v1 唯一实现 = `VolcengineLivePlatformAdapter`

## 后果 (Consequences)

### 正面
- 直播相关代码量极少：App 端仅 WebView + 预约逻辑；后端仅场次管理 + 火山 URL 下发
- 推流稳定性、互动稳定性由火山专业团队保障
- 避免了 IM 长连接、防作弊、内容审核等深坑

### 负面
- **直播间 UI 受火山约束**：与 App 整体设计语言可能不一致
- 学员行为数据（点赞、聊天）我们拿不到（除非火山有 webhook） → 此类互动无法纳入积分体系
- **强依赖火山产品形态**：如果火山某天调整 API、改 UI、改计费，我们被动响应

### 假设风险（必须验证）
1. 火山引擎直播 SaaS 是否提供完整直播间 H5 页（包含聊天、互动）？
2. 火山是否支持"按 liveId 动态下发个性化 URL"（含权限控制）？
3. 火山是否支持回放（v1 状态机包含"可回放"状态）？
4. 火山是否有 webhook 上报"观看时长 / 观看用户"，让我们做积分？

→ **采购对接阶段必须逐项确认**，若有缺口可能需要补做。

### 实施约束
- 后端必须通过 `LivePlatformAdapter` 接口访问火山，禁止业务代码直接调用火山 SDK
- 火山的 appId/secret 必须从配置文件读取，不写代码硬编码
